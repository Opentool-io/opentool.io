What is OpenTool?

AI tools are non-deterministic. You cannot control what they will generate, suggest, or attempt. But you can be deterministic about what they won't execute. That distinction matters more than most people realize.

OpenTool is an open-source framework for governing AI development tools. It gives you RBAC, capability gating, guardrails, budget enforcement, and a plugin registry — so every AI agent in your org operates within boundaries you define. Not after the fact. Before.

Think of it like OpenTelemetry for AI governance. A shared foundation that enterprise platforms build on. The plumbing that makes "AI in production" mean something other than "fingers crossed."

How We QA'd 20 UI Surfaces in One Session

April 2026 8 min read Sean Coady

We started the session with 8 working sidebar routes and 5 orphaned components that led nowhere. By the end, every surface was live, tested, and the RBAC engine was blocking rm -rf in production.

This is the story of how we took OpenTool from "impressive demo with dead links" to "every route works, every API responds, every guardrail fires." In about 30 minutes.

The Problem

When we sat down to audit the codebase, the picture wasn't great. Five UI workbenches — Benchmark, Drift Monitor, Architecture Map, Session Replay, and Provenance Tracker — existed as fully built React components. Good code. Proper state management. But they had no routes. Nothing linked to them. They were dead code sitting in src/components/, invisible to anyone who actually launched the app.

The agent chat surface had full SSE (Server-Sent Events) plumbing. WebSocket fallback. Streaming token display. But nobody had tested it end-to-end against a real backend. It rendered, technically, but the first message would silently fail and the UI would just... sit there.

Meanwhile, the sidebar showed 8 items. The app actually had 20 distinct surfaces. More than half the product was hidden.

The Fix (30 Minutes)

The approach was systematic. No heroics, no rewrites. Just wiring.

First, every orphaned component got a route in App.tsx. We added all 12 missing paths and confirmed each one rendered without crashing. Some needed props that previously came from nowhere — those got default values.

Second, we added backend API stubs. Not mocks. Actual Express handlers that return valid JSON with realistic shapes, so components degrade gracefully even when the real engine isn't running. The stub for /api/benchmark/results returns three sample runs with timestamps and percentile data. The stub for /api/drift returns a config diff. Real enough to test against, light enough to ship as defaults.

Third, the sidebar went from a flat list of 8 items to 20 routes organized into three groups: Primary, Analytics, and System.

# Before: 8 sidebar items, 5 orphaned components
# After: 20 routes, zero dead links, 31 Playwright tests

$ npx playwright test
  31 passed (4.0s)

Every route resolves. Every API endpoint returns valid JSON. Every component renders without errors. That's the baseline — not impressive, just correct. The kind of correct that most products skip.

The RBAC Engine

With the UI stable, we turned to the part that actually matters: the authorization layer.

We built src/engine/auth.rs from scratch. Three core functions: check_capability, check_budget, and evaluate_guardrails. Each one is pure — takes an entity, a set of rules, and a context, and returns an allow/deny decision with a reason. No side effects. No database calls. Just logic.

Then we wired it into the web API and tested it:

# Alice tries to edit a file — allowed
$ curl -X POST /api/auth/check \
  -d '{"entity_id":"dev-alice","capability_id":"file-write"}'
{"decision":"allow"}

# Alice tries rm -rf — guardrail blocks it
$ curl -X POST /api/auth/check \
  -d '{"entity_id":"dev-alice","capability_id":"shell","action":"rm -rf /"}'
{"decision":"deny","reason":"guardrail: Confirm before executing destructive commands"}

That's the core thesis: you can't control what an AI will generate. But you CAN be deterministic about what it won't execute.

The guardrail engine evaluates a chain of rules. Each rule has a pattern (regex or glob), a severity level, and an action (deny, warn, or require-confirmation). Rules compose. The most restrictive match wins. If no rule matches, the default capability grant applies.

We wrote 22 unit tests for the auth module alone. Edge cases matter here — what happens when an entity has two roles with conflicting grants? What if a budget is exactly at the limit? What about nested capability inheritance? Every case has a test. Every test has a name that describes the scenario in plain language.

The Plugin System

The doc-manager plugin went from concept to working package in one pass. It ships with resource specs (what file types it manages), routing rules (which requests it intercepts), and format linting (it rejects malformed documents before they hit the engine).

The interesting part: it includes the first-ever team.json — a manifest that declares what agent personas a plugin needs to operate. The doc-manager needs a "reviewer" persona (can read and comment) and an "editor" persona (can read, write, and restructure). When you install the plugin, the RBAC engine automatically provisions these personas and binds them to the roles you've configured.

That's the plugin contract. You declare your needs, the platform provisions them, and your plugin never has to think about auth again. It just works within the boundaries the org has set.

The Testing Philosophy

Every route gets a Playwright test. Not as an afterthought. Not because someone filed a ticket. The test is the proof that the thing works. If there's no test, it doesn't ship.

Our visual-qa suite does three things:

First, it navigates to each of the 20 sidebar routes and confirms the page renders without console errors. Simple, but you'd be surprised how many shipped products fail this check.

Second, it hits every API endpoint and validates the response is well-formed JSON with the expected top-level keys. Not deep schema validation — just enough to catch the "endpoint returns HTML error page instead of JSON" class of bugs.

Third, it screenshots every surface at three viewport widths: 1440px, 768px, and 375px. These screenshots go into a qa-evidence/ directory that we review before every release. Not automated visual diffing (yet) — just a human looking at 60 screenshots and checking that nothing is obviously broken.

What This Means

If you're running AI agents in production — Claude Code, Cursor, Copilot, whatever — and you don't have a governance layer, here's what you're betting on: that every prompt, every tool call, every file operation will be benign. Every time. Across every developer. Across every agent session.

That bet fails eventually. One bad prompt deletes a production database. One leaked context window exposes credentials. One runaway loop burns through your API budget in twenty minutes. These aren't hypotheticals. They're incident reports we've read.

OpenTool is the layer that sits between the agent and the action. It doesn't slow anything down — capability checks take microseconds. It doesn't require you to change how you work. It just ensures that the things that must not happen, don't happen.

Open source. Local-first. And now, tested across every surface.

We're building in the open. The repo is live. The tests are green. Come break things.
